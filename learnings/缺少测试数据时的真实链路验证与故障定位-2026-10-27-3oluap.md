## Context

当测试环境缺少足够多页、足够大载荷或完整字段形态的数据时，Mock 和首屏成功只能验证局部流程，不能证明真实分页与 AI 证据链正确。应在编码前明确哪些假设必须由有代表性真实数据的开发或联调环境验证，并把验证结果转成可重复的自动化测试。

## Solution

### 编码前建立可验证假设

1. 列出测试环境无法证明的关键假设，例如第二页及后续分页字段、排序方向、空数据与业务失败的差异、大页消息形态和 AI 正文预算。
2. 为每个假设指定验证环境、最小数据范围、只读操作和需要保留的证据。优先使用开发或联调环境中的已有真实会话，不发送、编辑或删除消息。
3. 证据只保留必要的请求字段、响应结构、状态码、条数、字段类型和 trace 信息；脱敏客户姓名、会话 ID、URL、Cookie 和消息正文。
4. 在实现前先形成接口证据链：上游响应 DTO、请求 DTO、Controller、查询条件、排序方式、客户端归一化逻辑，以及一个真实参考调用方的请求行为。

### 按严格契约实现

- 根据查询条件确定游标语义。例如查询条件为 `id < boundary` 时，应从当前页数据库 ID 计算下一页边界，而不是根据展示顺序或另一个业务标识猜测。
- 参考调用方用于验证接口真实可用和参数形态，但最终契约仍以提供方 DTO、Controller 和查询实现为准。
- 对错误输入采用明确校验和受控错误。不要用宽松类型转换、字段回退或多套游标兼容来掩盖未确认的契约。
- AI 数据链路需要同时验证“上游返回了正文”和“正文最终进入模型载荷”。页大小、结构化元数据、重复裁剪和累计预算都会影响最终可见内容。

### 把真实数据形态固化为测试

- 将脱敏后的真实响应结构转成测试夹具，至少同时包含数据库 `id`、业务 `msgId`、不同发送时间顺序、文本和非文本消息。
- 覆盖第二页、第三页和历史结束，断言请求边界、无重复、无跳页，并区分首次加载错误、历史加载错误、空结果和正常结束。
- 覆盖接近真实规模的大页载荷，断言 AI 在源头使用受控页大小，文本正文非空，长正文按预算截断，预算不足时返回明确错误。
- 同时保留接口契约测试、服务归属校验测试、AI 工具参数测试和最终模型载荷测试，避免只验证某一层。

### 线上或联调问题的定位顺序

1. 从容器日志或 trace 确认失败边界：前端、页面 API、服务层、CRM client 还是上游业务响应。
2. 对比首屏成功请求与翻页失败请求，只关注变化字段，例如游标、方向和页大小。
3. 沿“前端参数 -> API 校验 -> 服务归属校验 -> client 请求体 -> 上游 DTO/查询”逐层缩小，直到找到首个语义不一致的位置。
4. 对 AI 正文缺失，同时检查工具 trace 中的返回条数、非文本数量、裁剪告警、页预算和累计预算；不要只检查上游响应里是否存在正文。
5. 修复后执行相关单测、完整测试、类型检查、lint 和生产构建，再回到真实多页会话验证连续分页，并检查 AI trace 中正文确实进入模型证据。

## Lessons

- 缺少代表性测试数据时，应在编码前登记必须通过真实环境验证的假设，而不是把环境空数据视为契约证据。
- 最有效的定位方式是建立端到端证据链，并比较成功请求与失败请求的最小差异。
- 真实问题修复后要把数据形态转成测试夹具，使后续回归不再依赖同一条真实会话。
- Mock 和首屏测试不足以证明真实分页；宽松回退会掩盖错误契约；重复裁剪可能让元数据挤掉正文。
