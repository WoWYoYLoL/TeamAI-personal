## Context

测试环境缺少多页记录、大载荷、异常字段或其他代表性数据时，环境验证无法在编码前证明完整行为。此时更需要从代码源头梳理契约：源码梳理是实现前置，环境验证只负责最终确认源码之外的运行时事实。字段名、Mock、首屏成功和单个参考页面都不能替代提供方契约。

## Solution

### 建立完整的源码证据链

按下面的固定顺序追踪一次请求，并记录每层发生的语义变化：

| 层级 | 需要确认的内容 | 应留下的证据 |
| --- | --- | --- |
| 请求 DTO | 字段名、类型、必填性、默认值、范围和方向参数 | 请求契约表，标明数字、字符串、可空和边界范围 |
| Controller | 路由、参数绑定、校验、默认值、响应排序和错误映射 | 实际入口、校验条件及业务成功判定 |
| Service | 分支条件、权限、业务语义、分页方向和调用组合 | 字段如何参与业务决策，哪些值会进入查询层 |
| Repository/SQL/查询条件 | 比较运算、排序、limit、索引字段和空结果 | 例如 `id < boundary`、升序或降序、先排序还是先截取 |
| 响应 DTO | 字段来源、类型、可空性、业务标识与数据库标识 | 响应字段映射表，明确哪些字段真实存在 |
| 调用方 | 归一化、权限封装、重排、分页状态、裁剪和展示 | 数据从上游响应到最终页面或模型载荷的完整路径 |

梳理时重点回答六个问题：字段从哪里来、类型是什么、业务语义是什么、按什么顺序返回、下一页如何计算、空值和错误分别表示什么。只有所有层级一致时，才把结论写入实现。

### 横向比较多个调用方

查找至少一个已经工作的调用方，与待修改调用方逐项比较：

- 比较实际请求体、会话或认证信息、参数类型、分页边界、排序和错误处理。
- 把提供方 DTO 与查询逻辑支持的行为归为“数据源通用契约”。
- 把调用方新增的权限校验、页大小、预算、缓存、归一化和展示顺序归为“调用方策略”。
- 参考调用方只能用于交叉验证和发现差异；发生冲突时，回到提供方的 DTO、Controller、Service 和查询层确定契约。

这种比较可以快速识别“接口本身不可用”和“某个调用方解释错误”的差别，也能避免把某个页面的局部实现误写成所有接入方都必须遵守的规则。

### 编码前输出三个结果

1. **契约表**：列出请求字段、响应字段、类型、来源、默认值、排序、分页方向、空值和错误语义，并附源码位置。
2. **不变量**：写出实现必须始终满足的规则，例如分页边界只能来自数据库 ID、下一页不得越过未交付的数据、失败不能伪装成空结果。
3. **未验证假设**：只保留源码无法证明的运行时事实，例如真实数据规模、网关行为、登录态透传或线上数据是否超出声明范围，并为每项安排最小只读 smoke test。

能够从源码确认的内容应严格按契约实现，不增加字符串转换、字段回退或多套分页兼容。源码确实无法确认的部分要显式保留为假设，不能通过宽松兼容让错误暂时不暴露。

### 从真实数据形态和源码边界设计测试

- 构造第二页、第三页和历史结束，断言比较条件、下一页边界、无重复和无跳页。
- 构造消息发送时间与数据库 `id` 顺序不一致，确认展示排序不会改变分页语义。
- 分别覆盖真实空数据、前置标识缺失、HTTP 错误和业务临时错误，保证调用方不会把失败解释为空结果。
- 使用接近默认上限的页大小和超长正文，验证结构化元数据、正文和分页信息在各层转换后仍符合预算。
- 对 AI 或其他载荷裁剪场景，断言上游正文存在、最终模型载荷正文仍存在，并验证裁剪范围与返回游标一致；无法容纳最小证据时应显式失败。
- 将脱敏后的真实结构固化为测试夹具，但测试断言应来自源码契约，而不是照抄某次偶然响应。

### 用真实环境补充验证

源码梳理完成后，真实环境只验证源码不能覆盖的运行时事实。验证应使用最小只读请求，记录状态码、字段类型、条数、trace 和分页结果，不保留客户标识、凭据、URL 或消息正文。验证结果如果与源码冲突，应先确认部署版本和网关转换，再决定修改提供方契约或调用方实现。

### 问题出现后的快速定位

1. 从日志或 trace 判断失败发生在页面、业务 API、Service、下游 Client、数据服务还是最终模型载荷。
2. 对比成功首屏与失败翻页的最小差异，优先检查游标值、类型、方向和页大小。
3. 沿同一条“请求 DTO -> Controller -> Service -> Repository/SQL -> 响应 DTO -> 调用方”链路逆向核对，定位第一个语义发生变化的位置。
4. AI 正文缺失时，逐层检查上游响应、归一化结果、工具结果、预算裁剪和最终模型载荷，列出所有裁剪点及每次裁剪前后的行数和正文大小。
5. 修复后先用契约测试固定根因，再做真实环境 smoke test，确认连续分页、正文可见和错误语义与源码结论一致。

## Lessons

- 测试环境没有代表性数据时，源码证据链应更完整，而不是降低确定性要求；环境验证不能替代实现前的契约证明。
- 多调用方对照可以帮助发现差异，但提供方源码才决定通用契约，调用方自己的权限、页大小和预算必须单独标注。
- Mock 或首屏成功无法证明真实分页；按字段名猜语义和过度兼容会掩盖错误；多层重复裁剪可能在上游正文正常时仍让最终内容丢失。
- 最有效的回归资产是契约表、不变量、边界测试和少量运行时 smoke test，而不是长期依赖某条真实数据。
